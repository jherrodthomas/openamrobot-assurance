## 1. What a scenario test is

A scenario is a world, a command profile on a named input topic, optional faults and checks
([`scenarios.yaml`](scenarios.yaml)). Each check names a property and the outcome the record predicts on each target
(`holds`, `violated` or `not exercised`) and why. **A test passes when the simulation shows what the record says.**
A known gap that is still there passes; a gap that closes, or a property that breaks, fails. The record and the
software therefore cannot drift apart unnoticed: when upstream fixes a gap, the test goes red until the prediction,
and the record behind it, is updated.

| Property | Holds when |
|---|---|
| `advances` | the robot's true position moves at least `min_m` over the run |
| `no_contact` | the footprint of `nav2_params.yaml` never comes within 0.03 m of an obstacle, judged from Gazebo's true pose, not odometry |
| `monitor_engaged` | the collision monitor reports stop, slow down or approach at least once |
| `stops_after_fault` | after the fault the robot comes to a standstill within `limit_m`; `not exercised` when it was already standing |
| `reverse_speed_le` | the true reverse speed never exceeds `limit_mps` |

## 3. The findings

### 3.1 At the baseline the scan filter keeps the robot's own body

At BL-001 the simulated robot does not move on the path Nav2 uses. The LiDAR was turned round on 12 October
(`lidar_joint` yaw π), but the sim scan body filter, a laser_filters angular-bounds chain that keeps one window of
±2.443 rad in the LiDAR frame, was not changed. It now removes the robot's forward 80 degrees and keeps the returns
from the robot's own body. The collision monitor sees an obstacle inside the footprint and holds the robot still.
GZ-02 shows it: monitor action 3 (approach) from the first sample, nothing reaches the base.

Upstream found the same and replaced the filter after the baseline: `7494771`, "switch sim scan body filter to
per-sector masking (issue #74)", masks the LiDAR sector −35 to +31 degrees at every range. That sector is the rear of
the robot, so on upstream main the simulated robot drives and stops for what it can see ahead, and is blind behind
it, as GAP-35 says of the real robot.

### 3.2 On upstream main the monitor cannot both drive and stop

On upstream main the robot drives, but it also drives into the tall box of GZ-02, the positive control, and the
monitor never acts. The simulated LiDAR's minimum range is 0.40 m (`gazebo_control.xacro`), and the LiDAR sits
0.085 m behind the footprint's front edge. Anything closer than 0.315 m ahead of the robot is therefore out of the
scan. The approach polygon looks ahead `time_before_collision` 0.8 s, which is 0.16 m at 0.20 m/s. The box leaves the
scan before it comes inside the look-ahead. The trace's `scan_min`, the nearest return the monitor receives, shows
it: about 0.92 m at the start, then nothing once the box is 0.40 m from the LiDAR.

GZ-06 sets the minimum range to 0.05 m, the RPLIDAR S3 datasheet value (to be checked against the datasheet of the
mounted unit). Then the scan shows parts of the robot's own model: two posts at 0.23 to 0.27 m, at −38 to −36 and +32
to +38 degrees, just outside the sim mask, and the side features at ±85 to ±91 degrees. The monitor holds the robot
still again. Upstream measured its sim mask with the 0.40 m minimum hiding these returns. The real robot's filter,
`scan_body_filter_real.yaml`, masks −45 to +49 degrees and the near returns at ±73 to ±96 degrees, and would cover
both.

### 3.3 What the findings mean

Both are recorded under GAP-40 (simulation and real robot differ). Neither changes the hazard picture of the real
robot, whose filter and LiDAR are different. They mean that no simulation result on the monitored path says anything
about the collision monitor until upstream's sim LiDAR and sim mask agree with each other and with the real sensor.
On upstream main that would take a minimum range near the real one, with a mask that covers the posts. When a
baseline takes up such a change, its target replaces `bl-001` here and the predictions are re-recorded.

## 4. How it runs

```
assurance/sim/gazebo/run.sh            # every scenario on every target; writes results/traces/<target>/ and results/
assurance/sim/gazebo/run.sh GZ-02      # one scenario
python3 assurance/sim/gazebo/evaluate.py --check    # what CI runs on every pull request: results current, all pass
```

1. [`prepare.sh`](prepare.sh) fetches the pinned sources into `docker/context/`, so the image build needs no network.
2. [`docker/Dockerfile`](docker/Dockerfile) builds one image per target on the pinned Nav2 Jazzy image: laser_filters
   and the Nav2 packages the collision monitor needs in a shared layer, then the software under test.
3. [`harness/scenario.launch.py`](harness/scenario.launch.py) starts, per scenario: the Gazebo server headless with a
   generated world ([`harness/world.py`](harness/world.py)), the robot description with the plant calibration and a
   pose publisher applied in memory ([`harness/calibrate.py`](harness/calibrate.py)), upstream's bridge, the scan
   body filter the target's own sim bringup starts, the collision monitor with upstream's `nav2_params.yaml`, and
   the driver.
4. [`harness/driver.py`](harness/driver.py) activates the collision monitor, publishes the footprint polygon it
   needs, plays the command profile on sim time, injects the faults and records a trace at 20 Hz.
5. [`evaluate.py`](evaluate.py) judges every check from the traces and writes the results.

The CI job [`gazebo.yaml`](../../../.github/workflows/gazebo.yaml) builds the images and runs every scenario on pull
requests that touch this folder, weekly and on demand, and judges the fresh traces (`--verify`); it keeps them as an
artifact and never commits. [`assurance.yaml`](../../../.github/workflows/assurance.yaml) runs `evaluate.py --check`
and the self-tests [`test_evaluate.py`](test_evaluate.py) on every pull request.

## 5. What is real and what is approximated

| Element | In these tests |
|---|---|
| Robot description, LiDAR model and mount, bridge | Upstream's, at the target commit, unedited |
| Scan body filter, collision monitor and its parameters | Upstream's, at the target commit; the scan passes a gate in the driver so that a dropout can be injected |
| Drive plant | Upstream's diff-drive plugin with the measured values of [`plant.yaml`](plant.yaml) in place of upstream's: track 0.46 m (0.400), ±0.71 m/s (±1.0), ±3.1 rad/s (±2.0); the replacement refuses to run if an upstream value has changed |
| Footprint | `nav2_params.yaml`'s local costmap footprint, published by the driver; there is no costmap |
| Navigation | None: the profile is published straight on the monitor's input (`cmd_vel_smoothed`) or on `/cmd_vel`; no planner, controller or velocity smoother |
| Obstacles | Static boxes and a cylinder for a person; no moving people |
| Contact | Footprint polygon against the obstacle's collision shape from Gazebo's true pose |
| Timing | Sim time; the headless server runs at about half real time, so no latency result is drawn from it |
